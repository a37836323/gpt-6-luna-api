gpt-6-luna API 调用参数说明：推理档位、端点选择与工具限制

gpt-6-luna 是 OpenAI 在 2026 年 9 月发布的推理模型，官方定位是「面向专注、大批量任务的最高效模型」。调用时最容易出问题的有三处：推理档位默认是 medium，不是 none；推理档位不为 none 时要去掉 temperature、top_p 等采样参数；在 Chat Completions 里调用函数只在 reasoning_effort 设为 none 时支持，要推理和工具一起用就走 Responses API。下面按官方模型页、GPT-6 使用指南、推理指南和更新日志逐项说明。

官方规格：上下文、输出上限与支持的端点

OpenAI 模型页列出的 gpt-6-luna 规格：模型类型为推理模型，当前快照就是 gpt-6-luna；上下文窗口 1,050,000 token，其中最大输入 922,000 token，最大输出 128,000 token；知识截止日期 2026-05-18。

输入支持文本和图片，输出只有文本。支持的端点是 Responses、Chat Completions 和 Batch。模型页列出的功能包括流式输出、Structured Outputs、函数调用、文件检索、图片输入、网页搜索和提示缓存。

Responses API 里可用的内置工具，模型页列了 web_search、file_search、image_generation、code_interpreter、hosted_shell、apply_patch、skills、computer_use、mcp 和 tool_search。注意模型页同时写明：内置工具和函数调用都应使用 Responses API。

计费方面，模型页写明输入超过 272K token 的请求整次按更高费率计费，Batch、Flex 与 Fast 各有不同费率，具体价格以官网价格页为准。

reasoning.effort 六个档位怎么设

gpt-6-luna 支持 none、low、medium、high、xhigh、max 六个推理档位，默认是 medium。推理指南也写明 GPT-6 Luna 省略推理档位时默认用 medium。参数写法因端点而不同：Responses 里写 reasoning.effort，Chat Completions 里写 reasoning_effort。

推理指南对各档位的一般说明是：none 适合对延迟敏感、不需要推理或多步工具调用的任务，例如语音、快速信息检索和分类；low 推理较省，延迟增加不多，适合需要工具调用、规划、搜索或多步决策的场景。档位越低越快、token 越少，档位越高思考越完整，模型也会按任务难度自适应地分配推理。

从旧模型迁过来时，GPT-6 迁移指南的建议是尽量保留原来实际生效的推理档位；原请求用的是 minimal 的，先改成 low，再用有代表性的任务对比效果。gpt-6-luna 支持 none，这一点和 gpt-6-astra、gpt-6.1-sol 不同，后两者不支持 none。

如果同一段对话里要临时调高或调低推理档位，迁移指南建议在标准的单智能体请求中使用 configuration_update 输入项，保持请求级的 reasoning.effort 不变，以免破坏提示前缀缓存；采用前先看推理指南里的兼容性限制。

什么时候必须去掉 temperature、top_p 和 logprobs

GPT-6 迁移指南写明：推理档位不为 none 时，要从请求里去掉 temperature、top_p 和 top_logprobs；用 Chat Completions 的还要去掉 logprobs；用 Responses 的要把 message.output_text.logprobs 从 include 数组里删掉。

因为 gpt-6-luna 的默认档位是 medium，请求里没有显式写 none 时，这条要求同样适用。常见情况是从旧代码直接把 model 改成 gpt-6-luna，但保留了原来的 temperature 设置，这时应先删掉这些参数再测。

如果业务确实依赖 temperature 或 logprobs，可以评估把推理档位设为 none 是否能满足质量要求；官方只说明了 none 以外的档位要去掉这些参数，没有说明 none 档下各采样参数的具体效果，需要用自己的任务验证。

带工具调用时选 Chat Completions 还是 Responses

模型页和迁移指南对 gpt-6-luna 的说法一致：Chat Completions 只有在 reasoning_effort 设为 none 时才支持函数调用；需要推理和工具一起用，应改用 Responses API。web_search、file_search 这类内置工具同样要走 Responses。

可以按这个顺序判断：只做纯文本或图片理解、不带 tools，两个端点都能用；带函数但任务不需要推理，可以留在 Chat Completions，把 reasoning_effort 设为 none；带函数且需要推理，或要用内置工具，就把这部分请求迁到 /v1/responses。

迁到 Responses 时，OpenAI 的 Responses 迁移指南建议逐个业务流程迁移：先改端点、请求体和输出解析；迁移函数定义，并确认回传的函数调用结果带有正确的 call_id；用了 Structured Outputs 的，把 schema 从 response_format 移到 text.format；流式消费端要改成处理 Responses 的类型化事件。

从 GPT-5.5 或更早版本迁来、并且用了提示缓存参数的，迁移指南要求把 prompt_cache_retention 换成 prompt_cache_options.ttl，取值为 "30m"。

图片输入：官方修复过一次图像编码问题

OpenAI 更新日志在 2026 年 9 月记录：修复了一个导致 GPT-6 Sol 和 GPT-6 Luna 图像理解能力下降的图像编码问题，修复后 API 和 Codex 里的视觉任务（包括电脑操作）结果有所改善。

官方建议：如果你的用例涉及图片输入，重新跑一遍评测，并重试受这个问题影响的工作流。也就是说，如果你在修复之前用 gpt-6-luna 测过看图效果并因此放弃，结论可能需要重新验证。

图片输入走 Responses 或 Chat Completions 都可以，模型页列出的输入模态是文本和图片。

通过 OpenLux 中转调用 gpt-6-luna 怎么验证

gpt-6-luna 目前在 OpenLux 价格接口中在售，列出的端点类型是 OpenAI 兼容的 Chat Completions 和 Responses，价格以官网价格页为准。

客户端或 SDK 的 Base URL 填 https://api.openlux.ai/v1，Chat Completions 请求 /v1/chat/completions，Responses 请求 /v1/responses；Key 在 OpenLux 控制台的「令牌」页创建。

验证分三步：先请求 /v1/models，能列出模型说明地址和 Key 都对，返回 401 说明 Key 错或没带上；再发一个最小请求，model 写 gpt-6-luna，只带一句输入和 low 推理档位，不带采样参数和工具，确认能拿到文本回复；最后再逐项加上 tools、图片或你需要的其他参数，哪一步出错就回到上面对应的小节排查。

中转对上述各参数的处理本文没有逐项核实，遇到报错以实际返回内容为准，并对照本文列出的官方限制排查。
